# Recurring Payment, Subscription Management & Billing Automation Platform

**Module 1 — Subscription Plans, Customer Models & Billing Cycle Engine**
**Module 2 — Invoice Generation, Proration Logic & Payment Webhook Handling**

An enterprise-grade billing platform backend built with **FastAPI**, **PostgreSQL**,
**SQLAlchemy 2.x**, and **Celery**, following Clean Architecture, SOLID principles,
the Repository Pattern, and a Service Layer.

> See `CHANGELOG.md` for a record of review passes and bug fixes made after
> the initial Module 1/2 build (e.g. a pagination `total` correctness fix).

## 2. Architecture

```
app/
  api/v1/          FastAPI routers (thin controllers only)
  core/             DB engine/session, base model mixins, JWT/security utils
  config/           Settings (pydantic-settings) & logging configuration
  models/           SQLAlchemy 2.x ORM models + enums
  schemas/          Pydantic v2 request/response models
  repositories/      Data-access layer (ONLY layer that queries the DB)
  services/         Business logic: state machine, billing engine, proration,
                     tax, invoice generation, mock payment gateway, webhook
                     sender/handler, refunds, audit log, etc.
  crud/             Low-level generic CRUD primitives used by repositories
  tasks/            Celery app + task definitions
  scheduler/        BillingSchedulerService (pure logic, unit-testable)
  middleware/       Exception handlers & request logging
  exceptions/       Custom exception hierarchy
  utils/            Shared helpers
tests/              Pytest suite (unit + integration)
alembic/            Migrations
```

**Request flow:** `API router` → `Service` (business rules, transactions, audit
logging) → `Repository` (SQLAlchemy queries) → `PostgreSQL`.

Controllers never touch the ORM directly, and repositories never contain business
logic — this keeps the codebase testable and swappable layer by layer.

## 3. Subscription State Machine

```
   ┌────────┐        activate         ┌────────┐
   │ TRIAL  │ ───────────────────────▶│ ACTIVE │
   └───┬────┘                         └───┬────┘
       │ cancel                 pause │   │ past_due (failed payment)
       ▼                               ▼   ▼
  ┌───────────┐    resume       ┌──────────┐   resume   ┌──────────┐
  │ CANCELLED │◀────────────────│  PAUSED  │──cancel───▶│ CANCELLED│
  └───────────┘                 └──────────┘             └────┬─────┘
       ▲                                                       │
       │                        ┌───────────┐  resume/re-activate
       └────────cancel──────────│ PAST_DUE  │─────────────────▶ ACTIVE
                                 └───────────┘
```

- `CANCELLED` is a **terminal state** — no transitions out of it.
- Every transition is validated by `SubscriptionStateMachine.assert_valid_transition`
  and rejected with `409 invalid_state_transition` if not allowed.
- Every transition is appended to `subscription_status_history` and recorded in
  `audit_logs`.

## 6. Typical API Flow

```bash
# 1. Register + log in
curl -X POST /api/v1/auth/register -d '{"email":"admin@co.com","full_name":"Admin","password":"..."}'
curl -X POST /api/v1/auth/login    -d '{"email":"admin@co.com","password":"..."}'
# -> {"access_token": "...", "refresh_token": "..."}

# 2. Create a plan
curl -X POST /api/v1/plans -H "Authorization: Bearer <token>" -d '{
  "name": "Pro Monthly", "price": 29.99, "billing_interval": "monthly",
  "trial_period_days": 14, "feature_entitlements": {"seats": 5}
}'

# 3. Create a customer
curl -X POST /api/v1/customers -H "Authorization: Bearer <token>" -d '{
  "name": "Acme Corp", "email": "billing@acme.com", "country": "US"
}'

# 4. Subscribe (starts in `trial`)
curl -X POST /api/v1/subscriptions -H "Authorization: Bearer <token>" -d '{
  "customer_id": "<id>", "plan_id": "<id>"
}'

# 5. Lifecycle operations
curl -X POST /api/v1/subscriptions/<id>/activate
curl -X POST /api/v1/subscriptions/<id>/pause
curl -X POST /api/v1/subscriptions/<id>/resume
curl -X POST /api/v1/subscriptions/<id>/cancel -d '{"cancellation_type": "immediate"}'

# 6. Change plan (Module 2: auto-applies proration if mid-cycle & active)
curl -X POST /api/v1/subscriptions/<id>/proration-preview -d '{"new_plan_id": "<id>"}'
curl -X POST /api/v1/subscriptions/<id>/change-plan -d '{"new_plan_id": "<id>"}'

# 7. Pay an invoice via the mock gateway, then refund it (Module 2)
curl -X POST /api/v1/payments/process -d '{"invoice_id": "<id>"}'
curl -X POST /api/v1/refunds -d '{"invoice_id": "<id>", "reason": "Customer request"}'
```

              │

## 10. Known Limitations (by design, scoped to later modules)

- **Failed-payment retry scheduling** (day 1 / day 3 / day 7 configurable
  backoff) is not yet implemented — a failed payment currently just marks the
  subscription `past_due` once; Module 3 adds the retry engine.
- **Downgrade credit is not banked.** When a mid-cycle plan downgrade yields a
  net credit (see section 11), no invoice is generated and the credit is not
  carried forward as an account balance — it's simply not charged. Carrying a
  running account-credit ledger is out of scope for this module.
- **PDF invoice export** (ReportLab, branding, itemized layout) is not yet
  implemented — Module 3 adds this.
- **Usage-based charges and discounts** have a reserved `InvoiceLineItemType`
  (`usage_charge`, `discount`) but no service currently populates them; no
  usage-metering module exists yet in this project's scope.
- The React.js admin dashboard is out of scope for this backend module.

These are covered by Modules 3–4 of the project plan.

### How proration works

`change-plan` only applies proration when the subscription is `active` **and**
its current billing cycle is still in progress (not yet billed). Trial,
paused, and past_due subscriptions simply swap plans — the next invoice uses
the new plan's price with no proration math.

```
net_amount = (new_plan.price × remaining_days/cycle_days)
           − (old_plan.price × remaining_days/cycle_days)
```

- **Upgrade** (`net_amount > 0`) → a proration invoice is generated immediately
  with `proration_credit` (unused old-plan time), `proration_debit` (new-plan
  remaining cost), and a `tax` line item if applicable.
- **Downgrade** (`net_amount ≤ 0`) → no invoice is generated (see Known
  Limitations above).

### How the mock payment gateway & webhooks work

`POST /payments/process` simulates a real gateway charge:
`settings.PAYMENT_GATEWAY_SUCCESS_RATE` (default 90%) determines success/
failure at random, and a `Payment` row plus a webhook event are created either
way — exactly mirroring how Stripe/Razorpay call back after settling a charge.

By default (`PAYMENT_WEBHOOK_URL` unset), the "webhook" is delivered
**in-process** — the sender calls the handler directly in the same DB
transaction, so the platform works end-to-end with zero extra infrastructure.
Set `PAYMENT_WEBHOOK_URL` to an externally reachable URL to test real HTTP
delivery instead; the sender then HMAC-signs the payload (`WEBHOOK_SECRET`)
and retries up to `WEBHOOK_MAX_RETRIES` times. The `/webhooks/payment`
endpoint verifies the `X-Webhook-Signature` header whenever one is present.

The handler is **idempotent**: replaying the same `paid`/`failed`/`refunded`
event for a payment already in that state is a safe no-op (`event_processed:
false` in the response) rather than a duplicate state change.

### Refunds

`POST /refunds` issues a full (default) or partial refund against any `paid`
invoice, adds a `refund` line item, and reduces the invoice total —
marking it `refunded` only once fully refunded (a partial refund leaves it
`paid` with a lower total). Additionally, **immediately cancelling** an
active subscription that has an already-paid invoice for its current cycle
automatically refunds the unused portion of that cycle — cancelling during
`trial` (nothing charged yet) or before any payment correctly creates no
refund.

### How email notifications work

Satisfies Module 2's "Payment Webhook Handler → Notifications" requirement:
customers get notified on **payment succeeded**, **payment failed**, and
**refund completed**. Dispatch is asynchronous via the existing Celery +
Redis infrastructure (`app/tasks/notification_tasks.py`) — the request
handling code (webhook handler for payments, `RefundService` for refunds,
since this app's refund flow doesn't route through the payment webhook)
only ever fires a non-blocking `.delay()` call, wrapped so a dispatch
failure (e.g. broker unreachable) is logged and swallowed rather than
breaking payment/refund processing.

By default (`SMTP_HOST` unset), notifications are **logged instead of
sent** — so this works out of the box with zero extra infrastructure,
matching the same "simulate by default" philosophy as the mock payment
gateway and in-process webhook delivery. Set `SMTP_HOST` (and
`SMTP_USERNAME`/`SMTP_PASSWORD` if your provider needs them) to send real
emails. Set `NOTIFICATIONS_ENABLED=false` to disable the feature entirely.

## 12. Customer Ownership Foundation (Phase 1A / 1B)

Ahead of building role-based/admin features, `Customer.user_id` links a
billing `Customer` record to the `User` account that owns it — nullable
(not every customer necessarily has a self-service login), unique (one
customer per user), FK to `users.id` with `ON DELETE SET NULL` so deleting
a `User` never deletes their billing history.

- **`GET /customers/me`** returns the calling user's linked customer, or
  `404` if none exists yet. `POST /customers` sets `user_id` automatically
  from the authenticated caller (no client-supplied `user_id` is ever
  accepted) and rejects a second customer for an account that already has
  one (`409`).
- **Ownership enforcement added in Phase 1C** (see section 13 below) —
  `GET/PATCH /customers/{id}` now require the caller to own the record
  (or be an admin).
- **Lazy-loaded ORM relationship only** (`Customer.user` / `User.customer`,
  `lazy="select"`) — fetching a `Customer` never triggers an extra
  join/query unless `.user` is explicitly accessed.
- The frontend's `CustomerContext` now resolves the linked customer via
  this single endpoint instead of a client-side localStorage cache +
  paginated email search across all customers — see the CineVerse
  frontend's own README/CHANGELOG for details.

## 13. Ownership Enforcement & Role-Based Authentication (Phase 1C)

Building on Phase 1A/1B's ownership link, this phase adds the actual
security checks and a minimal admin role.

- **`GET /auth/me`** returns the authenticated user's own account,
  including `is_superuser` — the frontend uses this to decide whether to
  show admin-only UI (there is no admin UI yet; see Known Limitations).
- **`get_current_superuser`** (`app/api/deps.py`) layers on
  `get_current_user`: 401 if not authenticated, 403 if authenticated but
  not `is_superuser`.
- **Customer ownership enforcement**: `GET /customers/{id}` now requires
  authentication (previously public) and, along with `PATCH
  /customers/{id}`, returns `403` if the caller doesn't own that customer
  and isn't an admin. `GET /customers` (list) is now admin-only. Internal
  service-to-service lookups (invoice generation, the billing scheduler,
  notifications) go through `CustomerRepository` directly and are
  completely unaffected — this check only applies to the two
  API-facing single-customer routes.
- **Plan mutations are now admin-only**: `POST /plans`,
  `PATCH /plans/{id}`, and `POST /plans/{id}/archive` require
  `get_current_superuser`. `GET /plans` and `GET /plans/{id}` remain
  public — plan browsing needs no auth at all, matching the existing
  landing page / plan-selection flow.
- **No self-service admin promotion, by design.** There is no endpoint
  that grants `is_superuser` — the first admin account is created by a
  direct database update (`UPDATE users SET is_superuser = true WHERE
  email = '...'`), the same way the test suite's `admin_auth_headers`
  fixture bootstraps an admin for testing. Adding a self-service "become
  an admin" endpoint would be a security hole, not a feature.
- **Extended to every resource in Phase 1D**: subscriptions, invoices,
  payments, and refunds gained the same ownership enforcement as
  `Customer` — see section 14 below. This was a known, explicitly-flagged
  limitation of Phase 1C, not left unaddressed.

## 14. Ownership Enforcement for Subscriptions, Invoices, Payments & Refunds (Phase 1D)

Closes the gap flagged at the end of Phase 1C: every resource that
belongs to a `Customer` now enforces the same ownership rule.

- **`app/services/ownership.py`** (new) — two shared helpers used across
  all four services:
  - `assert_owns_customer(resource_customer_id, requesting_user, db)` —
    for single-resource GET/POST-by-ID endpoints. Raises `403` unless the
    caller is an admin or the resource's `customer_id` matches their own
    linked customer.
  - `effective_customer_filter(requested_customer_id, requesting_user,
    db)` — for list endpoints. Non-admins are always scoped to their own
    customer, **regardless of what `customer_id` they pass or omit** —
    not validated-and-rejected, silently overridden. Admins get whatever
    filter they asked for, including none (= everyone).
- **Subscriptions**: `GET /subscriptions/{id}` and
  `GET /subscriptions/{id}/billing-cycles` now require authentication
  (previously public, like `GET /customers/{id}` before Phase 1C).
  `POST /subscriptions` verifies the target `customer_id` belongs to the
  caller. Every lifecycle action (activate/pause/resume/cancel/
  change-plan/proration-preview) enforces ownership on the loaded
  subscription.
- **Invoices**: `GET /invoices/{id}` and its `/payments` and `/refunds`
  sub-resources all enforce ownership (the sub-resources check the
  parent invoice's ownership once, up front).
- **Payments**: `POST /payments/process` enforces ownership on the
  target invoice before charging it. `GET /payments/{id}` resolves the
  payment's invoice to determine its owning customer (`Payment` has no
  `customer_id` column of its own).
- **Refunds**: `POST /refunds`, `GET /refunds/{id}`, and `GET /refunds`
  (list) all enforce ownership. `Refund` already carries `customer_id`
  directly, so its checks are the simplest of the four.
- **Internal callers unaffected, verified not assumed**: grepped the
  entire codebase before making any change — the billing scheduler,
  notification service, and webhook handler all access these resources
  via their repositories directly (never through the enforced service
  methods), so none of them pass through this new enforcement layer.
  `requesting_user` defaults to `None` everywhere, meaning "no
  enforcement context" — exactly what internal, non-request-driven code
  needs.
- **No database migration** — this phase is pure service/router logic
  reusing the `Customer.user_id` link from Phase 1A.

### Verified

- Full suite: 159/159 passing (134 existing + 25 new in
  `tests/test_ownership_enforcement.py`, covering cross-customer 403s,
  list-scoping, own-access-still-works, and admin-bypass for all four
  resource types).
- Live, real-server security tests (not just pytest) covering all four
  resource types: two independently registered customers, confirmed
  Customer B gets a genuine `403` attempting to view/pause/create-for
  Customer A's subscription, view Customer A's invoice or its payment
  history, refund Customer A's invoice, or view Customer A's refund by
  ID — and confirmed Customer A's own access and the admin's full-access
  bypass both continue to work correctly, over real HTTP against the
  real database.
- 8 pre-existing tests needed fixing: most were simply missing an
  `Authorization` header on a call to an endpoint that used to be public
  (e.g. `GET /subscriptions/{id}`); one
  (`test_payments_list_supports_customer_id_filter`) had an assertion
  describing the *weaker* pre-Phase-1D behavior ("pass someone else's
  customer_id, expect empty results") which Phase 1D's stronger "always
  scoped to your own, no matter what you ask for" behavior made
  obsolete — rewritten to verify the correct, stronger guarantee instead
  of weakened to fit.

## 15. Analytics Module (Phase 2)

Read-only, admin-only aggregation endpoints powering the future Admin
Dashboard. No new database tables — every metric is computed on demand
from the existing schema, reusing the existing repository layer
(extending a few repositories with new optional filters/aggregates where
a genuine gap existed, never duplicating logic that was already there).

All five endpoints require `get_current_superuser` — a non-admin gets
`403`, exactly like the Plan-mutation and customer-list endpoints from
Phase 1C. They are the only endpoints in the API that intentionally
aggregate across *every* customer; this is deliberate (that's the whole
point of a platform-wide dashboard) and doesn't conflict with Phase 1D's
ownership enforcement, which governs customer-facing endpoints only.

### `GET /analytics/dashboard`

Platform-wide summary counters.

```json
{
  "total_customers": 13,
  "active_customers": 9,
  "total_plans": 25,
  "active_subscriptions": 10,
  "cancelled_subscriptions": 1,
  "total_revenue": "42.26",
  "total_successful_payments": 2,
  "failed_payments": 0,
  "total_refunds": 7
}
```

- `active_customers` — distinct customers with at least one `active` subscription.
- `total_revenue` — sum of `total_amount` across currently-`paid` invoices (a refund reduces `total_amount` directly, so this is always net-of-refunds, not gross billings).

### `GET /analytics/revenue?date_from=&date_to=`

Both query params are optional (`YYYY-MM-DD`, inclusive), filtering on `Invoice.paid_at`.

```json
{
  "date_from": null,
  "date_to": null,
  "total_revenue": "42.26",
  "revenue_by_month": [
    { "month": "2026-07-01", "revenue": "42.26" }
  ],
  "revenue_by_plan": [
    { "plan_id": "2c5fc060-...", "plan_name": "Pro Monthly", "revenue": "21.36" },
    { "plan_id": "8712c360-...", "plan_name": "Starter", "revenue": "20.90" }
  ]
}
```

`revenue_by_plan` is attributed via each invoice's subscription's *current*
plan at query time (join through `Subscription.plan_id`), sorted highest
revenue first.

### `GET /analytics/subscriptions`

```json
{
  "total_subscriptions": 11,
  "active_subscriptions": 10,
  "trial_subscriptions": 0,
  "paused_subscriptions": 0,
  "past_due_subscriptions": 0,
  "cancelled_subscriptions": 1,
  "expired_subscriptions": 0
}
```

**`expired_subscriptions` is always `0`.** `SubscriptionStatus` has no
"expired" state in this schema — a subscription only ever becomes
`cancelled`, it never expires on its own. The field is kept (rather than
omitted) since the requirement said "if applicable" and a dashboard
consumer may reasonably expect the key to always be present; this is
documented here rather than silently returning a number that doesn't
mean anything.

### `GET /analytics/payments?date_from=&date_to=`

```json
{
  "date_from": null,
  "date_to": null,
  "total_payments": 2,
  "successful_payments": 2,
  "failed_payments": 0,
  "pending_payments": 0,
  "payment_trends": [
    { "month": "2026-07-01", "successful": 2, "failed": 0, "pending": 0 }
  ]
}
```

`payment_trends` groups by calendar month using `processed_at` (falling
back to `created_at` for the rare payment somehow never marked
processed).

### `GET /analytics/refunds`

```json
{
  "total_refunds": 7,
  "completed_refunds": 7,
  "pending_refunds": 0,
  "failed_refunds": 0,
  "total_refunded_amount": "210.23"
}
```

**Terminology mapping, since `RefundStatus` doesn't have "approved"/"rejected":**
`completed_refunds` is the closest equivalent to "approved" (money was
actually returned); `failed_refunds` is the closest equivalent to
"rejected" (the refund did not go through — an error during processing,
not a business decision to deny it). Rather than rename the response
fields to a vocabulary that doesn't exist anywhere else in this API
(every other endpoint uses `pending`/`completed`/`failed`), the real enum
values are used directly and documented here.

### Architecture notes

- **New file**: `app/services/analytics_service.py` (orchestration only —
  no query logic lives here beyond a small amount of Python-side
  reshaping of aggregate rows into response objects).
- **New file**: `app/schemas/analytics.py`, `app/api/v1/analytics.py`.
- **Extended, not duplicated**: `PaymentRepository` and `RefundRepository`
  gained an optional trailing `status` filter parameter (backward
  compatible — existing positional callers are unaffected, verified by
  grep before making the change and by the full pre-existing test suite
  passing unmodified afterward). `InvoiceRepository` gained
  `sum_paid_amount` / `revenue_by_month` / `revenue_by_plan`.
  `CustomerRepository` gained `count_active`. Everything else (`Total
  plans` via `PlanRepository.count()`, subscription status counts via the
  already-existing `count_all(status=...)`, etc.) reuses methods that
  existed before this phase, unchanged.

### Performance considerations

- Every endpoint issues a small, fixed number of aggregate SQL queries
  (no N+1 patterns, no per-row Python loops beyond reshaping already-
  aggregated rows).
- `revenue_by_month` / `revenue_by_plan` / `payment_trends` filter on
  `Invoice.paid_at` / `Payment.processed_at`, neither of which has a
  dedicated index today (only `Invoice.status` / `Payment.status` are
  indexed). At this project's scale this is a non-issue; if invoice/
  payment volume grows substantially, adding
  `CREATE INDEX ON invoices (paid_at)` (and the equivalent for
  `payments.processed_at`) would be a cheap, purely additive future
  migration — not done now, since it wasn't required and this phase was
  scoped to stay read-only/non-invasive (no deployment or schema
  changes).
- `count_active` (distinct customers with an active subscription) is a
  single `SELECT DISTINCT` subquery wrapped in a `COUNT` — efficient at
  any realistic scale for this project.

## 16. Invoice PDF Generation (Phase 4)

**`GET /invoices/{invoice_id}/pdf`** — downloads a professional, single-page
PDF of an invoice, generated entirely in-memory via ReportLab (already a
dependency since the initial scaffold, never used until now). Nothing is
persisted to disk — `Invoice.pdf_path` remains unused, exactly as before
this phase, and no Docker/volume changes were needed.

### Contents

Company name (CineVerse), invoice number, invoice date, customer name +
email, subscription plan, billing interval, amount + currency, invoice
status, payment status (from the invoice's most recent `Payment` record,
distinct from invoice status — "No payment yet" if none exists), payment
date (`Invoice.paid_at`), due date, the full line-item breakdown (reusing
the exact same line items Module 2's invoice generation already produces —
plan fee, proration credit/debit, tax — nothing new was computed), and a
footer with the generation timestamp.

### Architecture

- **New file**: `app/services/invoice_pdf_service.py` — the *only* new
  code in this phase. Contains zero query logic of its own; every piece
  of data (customer, subscription, plan, payments) comes from the
  existing repository layer, called exactly as any other service would.
- **Ownership enforcement reused, not reimplemented**: the new endpoint
  calls the exact same `InvoiceService.get_invoice(invoice_id,
  requesting_user=current_user)` used by `GET /invoices/{id}` and its
  `/payments`/`/refunds` sub-resources (Phase 1D) — a non-admin gets `403`
  for someone else's invoice, `404` for a nonexistent one, and an admin
  can download any invoice.
- **No schema change** — the PDF is built from data that was already
  fully queryable before this phase; no new column, table, or migration.

### Verified

- Full suite: 182/182 passing (175 existing + 7 new in
  `tests/test_invoice_pdf.py`).
- OpenAPI schema: 40 paths (39 + 1 new); every pre-existing path's shape
  unchanged.
- Live, real-server verification: generated a real PDF for a real paid
  invoice (with proration line items and a processed payment), confirmed

- A new test (`test_pdf_contains_expected_invoice_data`) doesn't just

  ("No payment yet", "—") instead of crashing on missing data.

## 17. Reports & Export Module (Phase 5)

Five admin-only report endpoints, each exportable as CSV, Excel (`.xlsx`),
or a summary PDF:

```
GET /reports/revenue?format=&date_from=&date_to=
GET /reports/customers?format=
GET /reports/subscriptions?format=
GET /reports/payments?format=&date_from=&date_to=
GET /reports/refunds?format=
```

`format` is `csv` (default), `xlsx`, or `pdf`, validated at the FastAPI
query-parameter layer itself (`pattern="^(csv|xlsx|pdf)$"`) — an invalid
value never reaches application code, it's rejected with a `422` before
any handler runs. Date-range filtering (`date_from`/`date_to`, inclusive,
`YYYY-MM-DD`) is offered only on Revenue and Payments — the two report
types where the underlying analytics already supported it (Phase 2);
Customers/Subscriptions/Refunds don't accept date params, matching exactly
what already existed rather than inventing new filtering capability.

### Architecture — two dedicated services, cleanly separated

- **`app/services/report_service.py`** (new) — answers "what goes in each
  report," nothing else. Every summary number is pulled directly from the
  existing `AnalyticsService` (Phase 2); every detail row comes from an
  existing repository's `list_all` (Customer/Subscription/Payment/Refund).
  Zero aggregation logic of its own.
- **`app/services/report_export_service.py`** (new) — answers "how is a
  report rendered," nothing else. Takes the generic `ReportData` the
  service above produces and renders CSV (stdlib `csv`), Excel
  (`openpyxl`, two sheets: `Summary` + `Detail`), or a PDF (ReportLab,
  reusing the same visual language as the Phase 4 invoice PDF) — never
  touches the database.
- **One small, necessary repository extension**: `PaymentRepository`
  gained optional `date_from`/`date_to` params (new trailing, backward-
  compatible params — verified via grep every existing caller is
  unaffected). Without this, the Payment Report's *summary* would respect
  a date range (via `AnalyticsService`) while its *detail rows* silently
  wouldn't — caught and fixed during this phase's own testing, not left
  as a hidden inconsistency.
- **Reports are generated synchronously, within a single request** — there
  is no background job queue. `_ROW_LIMIT = 10_000` caps CSV/XLSX detail
  rows (a pragmatic ceiling for this project's scale); the PDF further
  caps at 200 rows with a note pointing to CSV/Excel for the complete
  dataset, since a paginated PDF isn't the right format for a large flat
  dump. A platform with genuinely large datasets would want a real
  background export job — precisely why one wasn't built here without
  being asked for.

### Verified

- Full suite: 195/195 passing (182 existing + 13 new in
  `tests/test_reports_api.py`).
- OpenAPI schema: 45 paths (40 + 5 new); every pre-existing path's shape
  unchanged.
- Live, real-server verification of all 15 combinations (5 report types ×
  3 formats): every CSV parsed correctly with `csv.reader`, every XLSX
  opened correctly with `openpyxl` (`Summary`/`Detail` sheets, correct
  headers, row counts matching the summary numbers), every PDF confirmed
  via `file` as a genuine single-page PDF 1.4 document with the correct
  fields via `pdftotext`. Confirmed live: date range excludes out-of-range
  data on both Revenue and Payments; an invalid `format` value returns
  `422`; a regular customer gets `403` on every report endpoint; an
  unauthenticated request gets `401`.
- `openpyxl==3.1.5` added as a real (non-test) dependency —
  `requirements.txt`.

## 18. Email Automation (Phase 6B)

12 transactional email types, each with a shared, professional, responsive
HTML template (branded header with logo, support-contact footer,
copyright), plus a daily reminder scheduler. Every email is dispatched
asynchronously via the existing Celery + Redis infrastructure, and never
blocks or can break the action that triggered it.

### Event types & trigger points

| Event | Fires from |
|---|---|
| `welcome` | `POST /customers` (not `POST /auth/register` — the email needs the customer's name, and a `User` can exist with no `Customer`, e.g. an admin account) |
| `profile_updated` | `PATCH /customers/{id}`, only if a field actually changed |
| `subscription_started` | `POST /subscriptions` |
| `subscription_activated` | `POST /subscriptions/{id}/activate` |
| `subscription_paused` / `_resumed` / `_cancelled` | the matching lifecycle endpoint |
| `plan_changed` | `POST /subscriptions/{id}/change-plan` (subject reflects upgrade vs. downgrade) |
| `invoice_generated` | both invoice-creation paths: the billing scheduler and mid-cycle proration |
| `payment_succeeded` / `payment_failed` | the payment webhook handler |
| `refund_completed` | `RefundService` directly — refunds in this app don't route through the webhook handler |
| `trial_ending_reminder` / `renewal_reminder` | the new daily reminder scheduler (see below) |

### Configuration

Same "simulate by default" philosophy as every other integration point in
this project: leave `SMTP_HOST` unset and every email is logged instead of
sent, so this works out of the box with zero external dependencies. Point
`SMTP_HOST`/`SMTP_USERNAME`/`SMTP_PASSWORD` at any SMTP-compatible
provider (SendGrid, Amazon SES, Resend, Mailgun, etc. all expose one) to
send real email — no provider-specific SDK required. `COMPANY_NAME`,
`COMPANY_LOGO_URL`, and `SUPPORT_EMAIL` control the template branding.

### Trial-ending & renewal reminders

A new daily Celery Beat task (`run-reminder-scheduler`, separate from the
billing scheduler) finds subscriptions whose trial ends, or whose next
billing cycle renews, within `TRIAL_ENDING_REMINDER_DAYS` /
`RENEWAL_REMINDER_DAYS` (default 3 days each). Deduplication uses the
existing audit log rather than a new "last reminded" column — before
sending, it checks whether a `TRIAL_ENDING_REMINDER_SENT` /
`RENEWAL_REMINDER_SENT` audit entry already exists for that subscription;
if so, it skips. This means a subscription is never reminded twice for
the same trial/cycle no matter how often the scheduler runs, without any
new schema beyond the two audit event type values (added via a proper
`ALTER TYPE ... ADD VALUE` migration, applied to both databases).

### Verified

- Full suite: 226/226 passing.
- Live: dispatched the actual Celery task to a real running worker against
  a real backdated subscription, confirmed the reminder correctly fired
  once, confirmed the audit log entry exists in the real database, then
  confirmed re-running the task a second time correctly sends nothing
  (deduped).

## 20. Final Production Readiness Review

A complete backend↔frontend cross-check (does every implemented endpoint
have a real frontend UI?) surfaced one genuine, pre-existing security gap:

**`GET /audit-logs` and `GET /audit-logs/{entity_type}/{entity_id}` had no
ownership enforcement at all.** This router predates Phase 1D and was
never covered by it. Confirmed live, before fixing anything: a completely
unrelated customer could view any other customer's private audit trail,
or the entire platform's history, just by knowing (or guessing) an ID.

Fixed via a new `assert_owns_audit_entity()` in `app/services/ownership.py`,
resolving the owning customer per `entity_type` and reusing the existing
`assert_owns_customer()`. One deliberate exception: `entity_type=plan` is
exempt, since plans are already public data (`GET /plans` needs no auth
at all) — locking down their audit trail more than the resource itself
would be inconsistent, not safer.

Also closed the matching frontend gap: `auditLogService.list()` (the
list-all endpoint) existed but had no page calling it. Added
`AdminAuditLogPage` (`/admin/audit-log`), following the exact same list +
pagination + entity-type-filter pattern as every other admin page.

**Verified:** full suite 244/244 passing; live re-verification that the
exact cross-customer request which previously succeeded now correctly
returns `403`, while the legitimate owner and an admin both still get
`200`.
